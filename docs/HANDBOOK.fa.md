# راهنمای کامل BamdadDesk Control — نسخه ۱٫۲

این راهنما مربوط به پنل عمومی و کلاینت مدیریتی سازگار است. سازنده: **مهدی نصرتی** — [ایمیل](mailto:mahdinosrati06@gmail.com) — [تلگرام](https://t.me/MiNosrati).

## ۱. اجزای پروژه و نقش API

سه جزء مستقل داریم:

| جزء | مسئولیت | محل تنظیم |
|---|---|---|
| کلاینت BamdadDesk | ریموت، اجرای سیاست، ارسال وضعیت و گزارش | ویندوز سازمان |
| RustDesk OSS؛ hbbs و hbbr | پیدا کردن دستگاه و انتقال ارتباط ریموت | سرور لینوکس |
| BamdadDesk Control و API | مدیران، گروه‌ها، سیاست، ثبت دستگاه، گزارش و نسخه‌ها | Docker و مرورگر |

کلاینت درخواست HTTPS به API می‌فرستد. پنل به دستگاه داخل شبکه اتصال ورودی مدیریتی نمی‌زند. آدرس ID/Relay و کلید hbbs جای آدرس API و کلید امضای پنل را نمی‌گیرند. داشتن تنظیمات یکسان RustDesk برای ثبت در پنل کافی نیست؛ کلاینت باید قابلیت مدیریت BamdadDesk و پروفایل ثبت داشته باشد. نصب‌کنندهٔ سازمانی این پروفایل را خودکار آماده می‌کند.

## ۲. پیش‌نیاز و نصب از صفر

Ubuntu 22.04/24.04 یا Debian 12/13 با systemd، دسترسی root، اینترنت و معماری amd64/arm64. نقطهٔ شروع پیشنهادی ۲ هسته و ۲ گیگابایت RAM است؛ فضای دیسک متناسب با نسخه‌های EXE و بکاپ‌ها لازم است. دستور کامل نصب در README.fa.md قرار دارد و پیش‌نیازها را نصب می‌کند.

نصاب دربارهٔ حالت دسترسی، آدرس، پورت، نام مدیر و رمز سؤال می‌کند. سه حالت وجود دارد:

- HTTP با IP و پورت: بدون DNS و SSL، برای تست ایزوله. کلاینت مدیریتی به HTTPS معتبر نیاز دارد.
- HTTPS خودکار: دامنهٔ عمومی، DNS درست، TCP 80 آزاد و قابل دسترسی برای ACME، و پورت HTTPS انتخاب‌شده.
- پراکسی HTTPS موجود: پنل فقط روی loopback در دسترس می‌شود؛ مسیر پراکسی موجود را خودتان تنظیم کنید.

لینک تنظیم‌شده پیش از راه‌اندازی و هنگام خروج چاپ می‌شود. نمایش لینک به‌تنهایی نشانهٔ سلامت نیست؛ بررسی /healthz باید موفق شود. Docker موجود استفاده می‌شود و سرویس‌های دیگر متوقف نمی‌شوند. نصب اختیاری RustDesk در پایان پرسیده می‌شود؛ اگر سرور دارید «no» انتخاب کنید.

## ۳. منوی مدیریت لینوکس

```bash
sudo bash /opt/bamdaddesk-control/manage.sh
```

نصب جدید در صورت آزاد بودن نام، دستور `sudo bamdad` را هم ایجاد می‌کند. منو شامل وضعیت و آدرس، تغییر پورت/دامنه/حالت HTTPS، آپدیت با بکاپ، بکاپ، مدیریت RustDesk، وضعیت SSL و حذف پنل است.

```bash
sudo bash /opt/bamdaddesk-control/manage.sh configure
sudo bash /opt/bamdaddesk-control/manage.sh update v1.2.0
sudo bash /opt/bamdaddesk-control/manage.sh backup /var/backups/bamdaddesk-control
sudo bash /opt/bamdaddesk-control/manage.sh tls
```

آپدیت باید تگ دقیق منتشرشده داشته باشد. تغییر محلی فایل‌های ردیابی‌شده باعث توقف آپدیت می‌شود تا تنظیمات شخصی بازنویسی نشوند. بکاپ شامل دیتابیس، کلید امضای خصوصی، نسخه‌های کلاینت و .env است؛ فایل حساس است و باید خارج سرور هم نگهداری شود. API هنگام بکاپ کوتاه‌مدت متوقف و سپس شروع می‌شود. بازگردانی قدم‌به‌قدم در OPERATIONS.md آمده است. برگشت صرفاً به کد قدیمی بعد از مهاجرت دیتابیس کافی نیست.

حذف پنل فقط با تایپ دقیق `DELETE PANEL DATA` انجام می‌شود. دیتابیس، کلید امضا، نسخه‌ها و volumeهای همین پنل حذف می‌شوند؛ Docker، بکاپ‌ها و سرور RustDesk مستقل حفظ می‌شوند. پس از حذف کلید و دیتابیس، نصب تازه هویت قبلی پنل را ندارد.

## ۴. SSL رایگان

گزینهٔ HTTPS خودکار از Caddy استفاده می‌کند. صدور و تمدید گواهی خودکار است؛ cron یا نصب x-ui لازم نیست. گزینهٔ SSL منو امکان انتخاب این حالت، بررسی گواهی عمومی و دیدن لاگ Caddy را می‌دهد. برای گواهی خودتان یا پراکسی موجود، حالت دوم نصب را انتخاب کنید و تمدید را در همان پراکسی انجام دهید. منو کلیدهای گواهی پراکسی‌های دیگر را تغییر نمی‌دهد.

خطای صدور را با DNS، پورت 80 و فایروال ارائه‌دهنده بررسی کنید. گزینهٔ بررسی گواهی اعتبارسنجی TLS را خاموش نمی‌کند. هنگام تغییر IP یا دامنه، گواهی معتبر مقصد باید از قبل آماده باشد.

## ۵. RustDesk همراه پنل

```bash
sudo bash /opt/bamdaddesk-control/manage.sh rustdesk install
sudo bash /opt/bamdaddesk-control/manage.sh rustdesk status
sudo bash /opt/bamdaddesk-control/manage.sh rustdesk key
sudo bash /opt/bamdaddesk-control/manage.sh rustdesk logs
sudo bash /opt/bamdaddesk-control/manage.sh rustdesk configure
sudo bash /opt/bamdaddesk-control/manage.sh rustdesk backup
sudo bash /opt/bamdaddesk-control/manage.sh rustdesk update
```

نام عمومی سرور، پورت ID و Relay پرسیده می‌شود. پیش‌فرض‌ها: TCP 21115، TCP/UDP 21116، TCP 21117. پورت قبل از ID نیز رزرو می‌شود. بازکردن فایروال میزبان و ارائه‌دهنده با مدیر است. ارتباط مرورگری در این نسخه ارائه نمی‌شود؛ پورت‌های WebSocket منتشر نمی‌شوند.

داده و کلیدها در `/var/lib/bamdaddesk-rustdesk/data`، تنظیمات در `server.env` کنار آن و Compose با نام مستقل `bamdaddesk-rustdesk` قرار دارند. `start`، `stop` و `restart` هم پشتیبانی می‌شوند. آپدیت، تگ عددی مشخص می‌خواهد و قبل آن بکاپ می‌گیرد. بکاپ این بخش شامل کلید خصوصی hbbs است؛ آن را عمومی نکنید. سرور قبلی به‌طور خودکار وارد مدیریت این اسکریپت نمی‌شود.

در پنل، Access policies → Global، آدرس ID، Relay و کلید عمومی را تنظیم کنید. تنظیم سیاست کلاینت، پورت واقعی Docker را تغییر نمی‌دهد؛ برای تغییر پورت شنونده از منوی لینوکس استفاده کنید، سپس سیاست کلاینت را هماهنگ کنید. وب‌پنل به docker.sock و اجرای فرمان root دسترسی ندارد.

## ۶. ثبت خودکار کاربران

۱. HTTPS معتبر پنل را آماده کنید.
۲. در Client releases نسخهٔ EXE سازگار با مدیریت BamdadDesk را بارگذاری کنید. EXE معمولی RustDesk کافی نیست.
۳. در Enroll devices، آدرس عمومی API را وارد و ثبت از نصاب سازمانی را روشن کنید؛ Save را بزنید.
۴. نسخه، برچسب، گروه، ساعت اعتبار و حداکثر تعداد دستگاه را انتخاب کنید؛ Download organization installer را بزنید.
۵. فایل `BamdadDesk-Setup.exe` را فقط به کاربران مجاز بدهید. این فایل مجوز ثبت دارد؛ در ریپوی عمومی یا سایت دانلود عمومی نگذارید.
۶. کاربر فایل را با تأیید UAC اجرا می‌کند. نصب سرویس و پروفایل انجام می‌شود؛ سرویس وقتی به HTTPS پنل برسد خودکار ثبت می‌شود.
۷. در Devices، آخرین حضور و Policy applied را کنترل کنید. کلاینت تقریباً هر ۶۰ ثانیه وضعیت را می‌فرستد؛ خطاهای شبکه می‌توانند این زمان را بیشتر کنند.

خاموش‌کردن ثبت خودکار فقط ثبت جدید از نصاب‌های سازمانی را متوقف می‌کند؛ دستگاه‌های قبلی همچنان مدیریت می‌شوند. توکن دستی مسیر جداگانه و صریح مدیر است. لغو توکن فقط مصرف بعدی آن را متوقف می‌کند. این قابلیت مسدودسازی اتصال ریموت نیست.

نصاب روی دستگاهی که پوشهٔ مدیریت موجود دارد آن را بازنویسی نمی‌کند. برای به‌روزرسانی از EXE معمولی نسخهٔ جدید استفاده کنید؛ نصاب سازمانی برای ثبت اولیه است. اگر نصب نیمه‌کاره مانده، پوشهٔ ProgramData را کورکورانه پاک نکنید؛ وضعیت سرویس و فایل private/enrollment.json را با دسترسی مدیر بررسی کنید. توکن منقضی را از فهرست تمدید کنید یا مجوز جدید بسازید.

## ۷. مدیران و رمزها

مدیر جدید نیازمند نام و رمز حداقل ۱۲ کاراکتر است. مجوزها و گروه‌های مجاز را انتخاب کنید. خطای اعتبارسنجی داخل پنجره نمایش داده می‌شود. دکمهٔ نمایش/مخفی‌سازی کنار ورودی رمز، فقط متن تایپ‌شده را نشان می‌دهد.

رمز مدیر با رمز اتصال ریموت متفاوت است. رمز ذخیره‌شده و متن توکن از هش قابل بازیابی نیستند. بخش سیاست، منبع رمز مؤثر را به ترتیب دستگاه ← گروه ← سازمان ← پیش‌فرض کلاینت مشخص می‌کند. برای تعویض رمز، مقدار جدید وارد کنید. تنظیم `Permanent + one-time` هر دو روش را فعال می‌کند؛ اعمال‌شدن سیاست را در وضعیت دستگاه کنترل کنید.

## ۸. گروه و توکن

گروه: تغییر نام، مشاهدهٔ اعضا، رفتن به سیاست گروه و انتقال دستگاه از ویرایش آن. حذف گروه نیازمند انتخاب مقصد است؛ اعضا منتقل می‌شوند، سیاست گروه حذف می‌شود، توکن‌های گروه لغو می‌شوند و دسترسی گروه از مدیران برداشته می‌شود. تاریخچهٔ گزارش حذف نمی‌شود.

توکن: برچسب، گروه، تاریخ انقضا، تعداد مصرف و ثبت باقی‌مانده نمایش داده می‌شود. تمدید از لحظهٔ ذخیره محاسبه می‌شود. توکن لغوشده دوباره فعال نمی‌شود. تعداد مصرف توکن‌های قدیمی نامشخص است و عدد ساختگی صفر نمایش داده نمی‌شود.

## ۹. گزارش اتصال‌ها

فیلتر تاریخ ابتدا/انتها، گروه، شناسهٔ مدیریتی دستگاه، نوع رویداد و جست‌وجوی نام/IP/شناسهٔ طرف مقابل یا نشست وجود دارد. تاریخ‌ها میلادی و UTC هستند. صفحه‌بندی ۱۰۰ رویداد است؛ CSV همهٔ نتایج مطابق فیلتر را می‌دهد، نه فقط صفحهٔ جاری. ستون occurred در CSV زمان Unix بر حسب ثانیه است.

این گزارش بر پایهٔ رویداد ارسالی کلاینت است، نه ضبط صفحه و نه گزارش قطعی همهٔ ترافیک شبکه. دستگاه خاموش، شبکهٔ قطع یا صف پر ممکن است رویداد کم داشته باشد. مدت از اولین رویداد authorized تا closed متناظر محاسبه می‌شود؛ برای صورتحساب استفاده نکنید. خروجی CSV متن ورودی طرف مقابل را در برابر اجرای فرمول Excel محافظت می‌کند.

## ۱۰. تغییر آدرس API و مهاجرت

برای کلاینت ۱٫۷ و بالاتر: DNS، پراکسی و HTTPS آدرس جدید را آماده کنید. هویت پنل، دیتابیس و کلید امضا را نگه دارید؛ بهترین راه در تغییر دامنه این است که هر دو آدرس به همان پنل و همان داده اشاره کنند. مقدار API در پنل را تغییر دهید و آدرس قدیمی را روشن نگه دارید. کلاینت پیام امضاشدهٔ آدرس جدید را از پنل قبلی می‌گیرد، پاسخ امضاشدهٔ مقصد را کنترل می‌کند و سپس آدرس را ذخیره می‌کند. گزارش‌ها و دریافت نسخه هم آدرس جدید را استفاده می‌کنند.

کلاینت قدیمی این مهاجرت را انجام نمی‌دهد؛ اول آن را به نسخهٔ سازگار ارتقا دهید. کلاینت آفلاین تا برگشت آنلاین و دریافت پیام، آدرس قدیمی را لازم دارد. قطع زودهنگام دامنهٔ قبلی نیازمند اصلاح محلی پروفایل با دسترسی مدیر خواهد بود. تغییر مقدار API در وب، DNS و تنظیم listen سرور را خودکار تغییر نمی‌دهد.

## ۱۱. توسعه، آزمون و نقشهٔ تغییرات

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r requirements.lock
python -m pytest -q
```

برای تست ساخت نصاب روی لینوکس، NSIS را هم نصب کنید: `sudo apt-get install nsis`. تست بسته‌بندی با فایل نمونه فقط ساخت EXE را بررسی می‌کند؛ اجرای واقعی نصب روی ویندوز آزمون جداست. Docker خود NSIS را نصب می‌کند.

| فایل | چه چیزی و چرا |
|---|---|
| control/administration.py | مدیریت چرخهٔ توکن و گروه، منبع رمز بدون افشای هش |
| control/organization.py | آدرس API، کلید ثبت خودکار، پروفایل و ساخت NSIS |
| control/installer/ | نصب سرویس و آماده‌سازی فایل مدیریت با ACL ویندوز |
| control/reports.py | فیلتر، صفحه‌بندی و CSV محدود به دسترسی مدیر |
| control/storage.py | جدول‌های افزایشی؛ دادهٔ قبلی حفظ می‌شود |
| static/administration.js | فرم مدیر، نمایش رمز، گروه/توکن و دربارهٔ ما |
| static/organization.js | تنظیم ثبت سازمانی و دریافت نصاب |
| static/reports.js | کنترل‌های گزارش و خروجی |
| manage.sh و scripts/ | عملیات مدیریتی لینوکس و سرویس اختیاری RustDesk |
| src/bamdad/management.rs در مخزن کلاینت | ثبت، سیاست و مهاجرت تأییدشدهٔ API |
| src/bamdad/audit.rs در مخزن کلاینت | ارسال گزارش به آدرس به‌روز پنل |

راهنمای ساخت کلاینت و پیش‌نیاز Rust/Flutter در `docs/bamdad/BUILD.fa.md` مخزن کلاینت است. مخزن عمومی پنل شامل سورس کامل فورک کلاینت نیست. هنگام توزیع کلاینت مشتق از RustDesk، سورس متناظر، مجوز AGPL و اعلان‌های بالادستی را نیز در اختیار دریافت‌کنندگان بگذارید.

## ۱۲. مرز اعتبارسنجی

آزمون API و تست مرورگر محلی، تست ساخت Rust و CI لینوکس معیارهای جدا هستند. قبولی آنها به معنی آزمون نصب روی تمام نسخه‌های ویندوز، صدور واقعی گواهی عمومی یا آزمون زیر بار سازمانی نیست. برای راه‌اندازی سازمانی ابتدا یک دستگاه آزمایشی و نسخهٔ پشتیبان داشته باشید. گزارش دقیق اجرای تست‌های این انتشار در CHANGELOG و یادداشت انتشار درج می‌شود.
